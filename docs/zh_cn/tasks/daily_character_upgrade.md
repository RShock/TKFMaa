# 领奖前角色强化两次

本流程是“奖励领取”的前置操作，不新增独立任务。用户明确要求通过ADB逐步观察后编码；观察到的客户端用语为“角色”“筛选排序”“角色等级”“未满Max”“升级”和“角色强化”。

## 观察依据与页面流转

1. 主页底部“角色”进入角色列表；星号右侧当前显示“调教房间”的按钮打开筛选排序，文字随当前排序条件变化，不绑定这个词。
2. 筛选面板下滚，找到“角色等级”一行。循环按钮依次为All、限Max、未满Max；只在本行已显示未满Max时点击确定。清除旧筛选后再设置此条件，避免前序调教条件残留。
3. 角色列表下半部卡片有Lv与当前等级；选一张完整可见卡片，点击右侧“升级”，进入“角色强化”的强化页签。
4. 最左侧绿色细管药水每瓶增加200exp。点击一次出现橙色选中数字1及+200exp，点击中下部“升级”提交。响应有明显延迟，输入成功不等于消耗已生效。
5. 本轮实机第一次由Lv1到Lv2，第二次由Lv2到Lv4；两次各消耗最低级药水1瓶。第二次结束后点击底部城堡回主页，进入已有任务奖励领取。

## 实现与限制

- `daily_character_upgrade.json` 统一分发当前截图：待确认消耗、完成回主页、强化页、筛选、角色卡、主页入口。动作后回到分发器，按钮未生效时有限再识别，不串联假定成功的坐标步骤。
- `character_upgrade.py` 负责动态计算与资源账目，不用Python循环运行页面任务。每次外层领奖调用最多两次提交，先预占额度，再发出中心点击；进程内保留待确认快照及累计次数，游戏重启重做不重置。
- 筛选行用标签图片在滚动区内定位，再只检查同一行右侧状态。角色卡用局部Lv数字OCR，接受大小写与空格，只选择完整可见卡片，不锁定角色名称或立绘。
- 只有强化页签、最左药水图、数字1及+200exp同时符合才提交。库存、经验与角色标题使用OCR安全复核；无库存、读数未知、其他药水已选或总经验不对时不提交。错误选择先用“一键解除”清空，不使用自动选取或高级药水。
- 提交后待最低级药水库存减少1、角色标题一致、选中标记与预览消失，才记录一次确认完成。两次按操作次数计，不按提升等级数计。等待超时或重启后无法确认时保守保留已预占次数，停止本轮强化，继续原领奖，不再提交不确定操作。
- 无未满级角色、最低级药水不足、识别超时或不明页面时说明未完成原因，返回主页继续领取已有奖励；不把未完成强化写成两次成功。任务奖励本身仍沿用既有失败与部分领取规则。
- 提交响应最多观察20秒，分发最多80次、筛选下滚最多6次、筛选状态切换最多6次。停止强化后可识图关闭筛选面板、点击城堡或完整返回按钮，只有实际看到无遮挡主页才移交领奖；回主页仍失败时沿用任务故障策略。
- 从其他页面进入或游戏重启回主页时重建角色筛选许可，保留提交次数。待确认提交优先于导航，不能为了找按钮离开尚未响应的强化页面；本轮不保证覆盖强化一次即满级后自动更换第二个角色的分支。
- 模板来自MuMu设备内部1080×1920截图，经Maa原生归一到720×1280后无损裁剪。点击定位用框中心，不依赖桌面窗口尺寸；阈值不代表实测识别率。

## 完成状态

已确认两次强化，或因明确不足／不确定而停止强化，并回到主页后，才移交 `DailyTaskRewardsStartAttempt` 的原领奖候选。完整任务完成条件仍由既有六页领奖与回主页确认决定；强化人工观察不代表新增代码已验证。

动作异常经 `DailyCharacterUpgradeRetryDispatch` 回到统一识别入口；避免同节点成功与异常出口重复路由，保留待确认提交与两次强化额度，不因输入失败重新初始化。
